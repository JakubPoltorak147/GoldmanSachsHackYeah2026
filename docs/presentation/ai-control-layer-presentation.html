How it works

one request, step by step

1

Validate

Strict HTTP boundary: exact fields, bounded text, server-owned ID.

2

Evaluate

Registered controls read the original text and return findings, never actions.

3

Decide

Central policy maps findings: BLOCK › REDACT › ALLOW, with safe reasons.

4

Record

A content-free audit event is flushed to stdout and committed to SQLite.

5

Dispatch

ALLOW once, REDACT transformed once, BLOCK zero target calls.

6

Observe

Completion is recorded; the dashboard reads safe evidence only.

If anything fails: invalid inputevaluation erroraudit error zero target calls

fail closed!

Every decision is structured, explainable and audited before eligible dispatch. Error responses carry fixed codes, never submitted text or exception details.

The moment of control

A simple outcome

users can trust

The decision engine makes the security posture visible in one line, while retaining the structured reasons behind it.

ALLOW
when

No finding maps to a stronger action.

then

Forward the original interaction exactly once.

REDACT
when

A supported PII finding needs protection.

then

Replace selected spans with [REDACTED] before forwarding.

BLOCK
when

A credential or known attack indicator is detected.

then

Make zero target calls and return a safe reason.

Central precedence: BLOCK› REDACT› ALLOW

the stronger action wins!

Current
limits

  • Output inspection is not part of today's build.
  • Auth and budgets are not enforced yet.
  • Policy reload is not available; policy is fixed until restart.
  • Remote providers are not integrated yet.
  • General secret and jailbreak detection is not claimed.

expansion points,
not hidden claims
